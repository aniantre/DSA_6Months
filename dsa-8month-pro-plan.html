Recursion + Backtracking on Arrays/Strings
Topic: Recursion, Backtracking · Pattern: Subsets, Permutations, Combinations, Pruning
Medium–Hard
TopicRecursion · Call Stack · Backtracking Framework
PatternsChoose–Explore–Unchoose · Pruning · State Reset

The Backtracking Template

  • Every backtracking problem = same 3 steps: Choose → Explore → Unchoose
  • Build candidate solution incrementally
  • Prune: if constraint violated, return early without exploring
  • State reset: undo the choice before next iteration
  • Result collected at valid leaf nodes

Concepts

  • Call stack: each recursive call is a stack frame
  • Recursion tree: visualize before coding
  • Memoization preview: store results to avoid recompute
  • Pass vector by reference to avoid copying
  • Handle duplicates: sort first, skip same-level duplicates

void backtrack(vector<int>& candidates, int start, vector<int>& current, vector<vector<int>>& result, int target) { if (target == 0) { result.push_back(current); return; } for (int i = start; i < candidates.size(); i++) { if (candidates[i] > target) break; // prune current.push_back(candidates[i]); // choose backtrack(candidates, i, current, result, target - candidates[i]); // explore current.pop_back(); // unchoose } }

Prefix Sum on Arrays
Topic: Arrays · Pattern: Prefix Sum, Running Sum, 2D Prefix
Medium
TopicArrays — range queries, cumulative sums
PatternsPrefix Sum · Prefix+HashMap · 2D Prefix Sum

Key Insight

  • prefix[i] = sum of arr[0..i-1]. Then sum(l,r) = prefix[r+1] - prefix[l]
  • Subarray sum = K: prefix + hashmap. Count prefix sums seen so far.
  • 2D prefix: matrix queries in O(1) after O(mn) build time
  • This pattern converts O(n) range queries to O(1)

When to Use

  • Multiple range sum queries on static array
  • "How many subarrays sum to K" type questions
  • 2D matrix region sum queries
  • Running count / product queries

The Two Window Templates

Pattern Recognition

  • Dynamic: longest substring with at most K distinct chars
  • Dynamic + exact: "exactly K" = "at most K" - "at most K-1"
  • Anagram/permutation in string → sliding window with freq map

The One Template

  • "First/last position of X" → lower_bound / upper_bound
  • "Array rotated at unknown pivot" → check sorted half
  • "Find peak element" → move toward higher side

Monotonic Stack Key Insight

  • Maintain a stack that is always increasing or always decreasing

TopicTreeNode structure · height · depth · null checks
PatternsTop-Down DFS · Bottom-Up DFS · Level-Order BFS

The Two DFS Mindsets

  • Top-down: pass info from parent to children. Good for: path sum, max depth, diameter.
  • Bottom-up: combine results from children. Good for: size, height, balanced check.
  • Return value from DFS = results from subtrees
  • Global variable trick: when you need a single answer across the whole tree
  • Level-order: use queue, process level by level

Pattern Recognition

  • "Max path sum through any node" → bottom-up, global max variable
  • "Right side view" → BFS level order, take last of each level
  • "Count nodes in complete tree" → binary search on height
  • "Diameter" → bottom-up: at each node, left_height + right_height

Trie Structure

TopicGraph as adjacency list · visited array · component counting
PatternsBFS shortest path · DFS flood fill · Multi-source BFS

Graph Templates

  • BFS: queue + visited set. Each level = one edge farther. Use for: shortest path in unweighted graph.
  • DFS: recursive or stack. Use for: connectivity, cycle detection, flood fill.

Pattern Recognition

DSU Template (Memorize This)

  • find(x): if parent[x]==x, return x. Else parent[x]=find(parent[x]); return parent[x];

  • Count components: start with n components, decrement on successful union

  • Dynamic connectivity: edges added one by one, query connectivity
  • "Merge groups" or "connect components" operations
  • Cycle detection in undirected graph (if same component → cycle)
  • Kruskal's MST algorithm uses DSU

Knapsack Variants

  • 0/1: each item used once. dp[i][w] = max val using items[0..i] with weight ≤ w. Reverse inner loop if 1D.
  • Unbounded: items reusable. Inner loop forward (allows reuse).
  • Partition subset: dp[i][s] = can we get sum s from first i elements?
  • Target sum: count ways. dp[s] += dp[s-num]

LIS O(n log n)

  • Maintain "tails" array: tails[i] = smallest tail of IS of length i+1
  • For each num: binary search in tails to find insertion position
  • Length of LIS = tails.size()
  • Russian Dolls = sort by width, LIS on height

LCS · Edit Distance · Grid DP
Topic: Two-sequence DP, Grid Paths · Pattern: LCS dp[i][j], Edit Distance, Min Path Sum, Maximal Square
Medium–Hard
TopicTwo-sequence problems · Grid path problems
PatternsLCS dp[i][j] · Edit Distance 3-way DP · Grid DP with obstacles

LCS + Edit Distance Family

  • LCS: dp[i][j] = LCS of s1[0..i], s2[0..j]. If chars match, dp[i][j]=dp[i-1][j-1]+1. Else max of left/top.
  • Edit Distance: if match→dp[i-1][j-1]. Else 1+min(dp[i-1][j], dp[i][j-1], dp[i-1][j-1]).
  • Distinct Subsequences: dp[i][j] = ways to match t[0..j] in s[0..i]
  • Uncrossed Lines: exactly same as LCS!

Grid DP Patterns

  • Unique paths: dp[i][j] = dp[i-1][j] + dp[i][j-1]
  • With obstacles: if obstacle, dp[i][j]=0
  • Min path sum: dp[i][j] = grid[i][j] + min(dp[i-1][j], dp[i][j-1])
  • Maximal square: dp[i][j] = min(dp[i-1][j], dp[i][j-1], dp[i-1][j-1]) + 1

Interval DP

  • dp[l][r] = answer for subarray/subproblem from index l to r
  • Iterate by length: for len in 2..n: for l in 0..n-len: r=l+len-1
  • For each (l,r), try all split points k in (l,r)
  • Classic: Burst Balloons, Matrix Chain, Palindrome Partitioning

Bitmask DP

  • State = bitmask of which elements are "used"
  • dp[mask][last] = best way to reach "last" having visited elements in mask
  • Enumerate submasks: for(sub=mask; sub; sub=(sub-1)&mask)
  • Works for n≤20. O(2^n × n) or O(3^n) for submask enum.

Interview Framework

Google Problem-Solving Framework

The exact mental process. Practice it until it becomes subconscious reflex.

01

Understand the Problem (5 minutes — never skip)

  • Read twice. Paraphrase it out loud in one sentence.
  • Read the constraints. n≤20 → backtracking/bitmask. n≤1000 → O(n²). n≤10⁵ → O(n log n). n≤10⁹ → O(log n).
  • Write 2 concrete examples yourself. Include a tricky one (duplicates, negatives, edge).
  • Ask clarifying questions: "Can values be negative?" "Is input sorted?" "Can there be duplicates?"
  • Confirm: "So I need to find X, given Y, with these constraints — correct?"
02

Identify the Pattern (3 minutes)

  • What's the data structure? Array → check prefix/window/two-pointer. Tree → check DFS/BFS. Graph → check connectivity/path.
  • What's being asked? Exist? Count? Min/Max? All solutions? → each maps to a different approach.
  • Constraint clues: "contiguous" → window. "substring/subarray" → window or prefix. "subsequence" → LCS/DP. "shortest" → BFS/Dijkstra.
  • Trigger words: "k-th" → heap. "all permutations" → backtracking. "dependencies" → topo sort.
03

Brute Force → Optimal (always state brute force first)

  • State brute force: "The naive approach is O(n²) because..." Even if obvious.
  • Identify the bottleneck: "The inner loop is O(n) — can we cache this?"
  • Optimize step by step with reasoning: O(n²) → hashmap → O(n). Or O(n) → binary search → O(log n).
  • Confirm optimal: "This should be O(n log n) time, O(n) space — which fits the constraints."
04

Write Clean C++ Code (15–25 minutes)

  • Meaningful names: left, right, maxSum, currWindow — never i/j/x as primary names.
  • Edge cases at top: if(nums.empty()) return 0; if(n==1) return nums[0];
  • Comment key logic only: "// shrink window when more than k distinct" — not every line.
  • Trace through your example manually after writing. Verify output matches expected.
  • Check off-by-one: binary search (lo+hi)/2 vs lo+(hi-lo)/2, ≤ vs <, 0-indexed vs 1-indexed.
05

Handle Follow-Ups Like a Senior Engineer

  • "What if the array is unsorted?" → "That breaks my approach because X. I'd need to sort first, adding O(n log n)."
  • "Can you do O(1) space?" → "Yes, by using two variables instead of the dp array. Here's how..."
  • "What if n = 10⁹?" → "Then we need O(log n) time — binary search on the answer might work..."
  • "What if there are duplicates?" → "Good catch. Let me check if my logic handles that... [check]... yes/no because..."
  • Never say "I don't know" and stop. Always say "Let me think... one approach might be..."

What Kills Candidates

Common Google Interview Mistakes

Especially relevant for senior engineers — some of these are more common with experience, not less.

❌ Jumping straight to code

Senior devs do this instinctively. They see the problem and start typing. The Google interviewer marks this as "doesn't think before acting."

✅ Spend 5 full minutes understanding

Even if you've solved a similar problem before. Confirm constraints, write examples, check edge cases before a single line of code. Interviewers respect this process.

❌ Skipping brute force

Jumping directly to the optimal solution without stating the naive approach first. The interviewer can't follow your thinking and can't give partial credit.

✅ Always state brute force first

"The naive O(n²) approach would be... but we can optimize by..." This shows systematic thinking. Even Google expects and rewards this structured escalation.

❌ Silent coding

10 minutes of silence while you code. The interviewer has no idea if you're on track or completely lost. This is the #1 signal of a failing interview.

✅ Narrate every decision

"I'm using an unordered_map here because lookups are O(1) average. I'm initializing left=0, right=0 for the sliding window. The invariant I'm maintaining is..."

❌ Claiming code is correct without testing

Writing code and saying "that should work" without tracing through an example. Senior engineers especially are prone to overconfidence here.

✅ Manually trace through your example

After writing, take your own example from Step 1 and trace through the code step by step. Say the values out loud. Catch your own bugs before the interviewer does.

❌ Ignoring edge cases

Not handling: empty array, n=1, all elements same, integer overflow (int overflow when multiplying two 10⁵ numbers), negative numbers.

✅ List edge cases before coding

"Edge cases: empty input returns 0. Single element is trivially the answer. Overflow: I'll use long long since n can be 10⁵ and values 10⁴, product can be 10⁹ — within int range but I'll use long long to be safe."

❌ Using experience as a crutch

With 7 YoE, there's temptation to rely on "I've seen this before" and skip steps. This leads to subtle errors and missed constraints specific to this variant.

✅ Treat every problem as new

Your experience helps you recognize patterns faster — use that for the "identify pattern" step. But still follow the full framework. Discipline, not shortcuts, wins Google interviews.

❌ Freezing on follow-ups

"I don't know" with silence. Follow-ups are designed to be hard — you're not expected to solve them completely. You're expected to think out loud.

✅ Structure your thinking aloud

"Interesting. If n is now 10⁹, my O(n) solution would TLE. Let me think... One approach might be binary search on the answer since the function is monotonic. Another might be..."

❌ Messy variable names and no structure

i, j, k, x, temp1, temp2. Functions that do 5 things. No comments on non-obvious logic. Hard to follow even for you, let alone the interviewer.

✅ Write like you're being code-reviewed

left, right, windowSum, maxArea. Extract a helper function if logic is complex. Add one comment on the key invariant. "This loop maintains the invariant that window contains at most K distinct chars."
